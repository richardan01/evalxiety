## 1. Trace review UI rules
- Build a custom tool, "the single most impactful investment" [faq]; a simple web app or spreadsheet suffices [judge].
- One trace per screen, trace-level label: Pass/Fail + notes + Defer; autosave every action [faq][skills].
- Keys: 1 Pass, 2 Fail, D Defer, U Undo, arrows, Cmd+Enter save-and-next; progress counter, jump-to-ID [faq][skills].
- Native rendering (markdown, collapsible JSON, tables); system prompt in `<details>`; tool JSON collapsed but reachable; tool call linked to its result; role-coloured left border; bold prices/dates/names [faq][skills].
- Strip raw HTML from LLM output; disable images [skills].
- One screen holds merchant metadata, system context and verification tools (e.g., DB search) [judge].
- Show pipeline version, eval scores, reviewer, outcomes; filter/search; flagged traces get add-to-dataset, file-bug, rerun [faq].
- No failure-tag picker until categories are defined [skills].
- Sampling logic outside the app [skills]; keep random traces in every batch [faq][judge].
- INFERRED: required "first failure" field with span picker; justification beside the cost basis, rate card and policy it cites.

## 2. Open/axial coding + taxonomy
- ~100 diverse full traces [faq][skills]; annotate ≥30 yourself before accepting LLM suggestions [faq].
- Stop when the last 20 traces show no new failure type [skills] / modes stop changing [faq].
- Open coding: Pass/Fail + note on the first failure only (errors cascade); observations, not explanations; user-visible parts first [faq][skills].
- No predefined rubric or failure list; expect criteria drift [faq][judge][skills].
- Axial coding after 30–50 traces: 5–10 distinct, actionable categories, one-sentence definitions, split by root cause [skills].
- LLM clustering only after human review, human-vetted (LLMs cluster on surface similarity) [skills].
- Re-label all traces, one binary column per category; rate = sum/n; prioritise frequency × impact; 2–3 refinement rounds [skills]; report rates by dimension combination with n [judge].
- Log non-model issues too, e.g. broken integrations [faq].
- Transition failure matrix: rows = last successful state, columns = first failing state [faq]. INFERRED states: parse_request → fetch_merchant → lookup_rate_card → compute_price → justify → respond.
- One domain expert as "benevolent dictator", not the developer or a proxy [faq][judge]; kappa only for human-vs-human [faq][skills].
- Fix prompt gaps, missing tools and bugs before building evaluators [faq][judge][skills].
- Re-run after prompt/model changes [faq][judge][skills]; ≥100 fresh traces per 2–4 weeks + 10–20 outliers weekly [faq].

## 3. Gold data + splits
- ~100 labels per failure mode [judge][skills] (100–200 [faq]); hand-validate every label [faq].
- ~50/50 Pass/Fail even if production is skewed [skills].
- Stratified train 10–20% (sole few-shot source) / dev 40–45% (iterate) / test 40–45% (run once, prompt frozen) [faq][judge][skills].
- CONFLICT: 30–50 per class in each of dev and test [faq][judge] vs across dev+test combined [skills]. INFERRED: meet the stricter.
- Current two-way dev/held-out split lacks train; add it or few-shots leak [skills].
- Test much worse than dev = overfit; restart with a new untouched test set [faq].
- CI set: 100+ examples from error discovery + confirmed failures; scores aren't comparable across dataset versions [faq].
- Synthetic: hand-write ~20 tuples, LLM expands, tuple→query in a separate prompt, run through the real system [faq][skills]. Synthesize inputs only, never AI responses [judge]. Can't estimate failure frequency; weak for high-stakes domains [faq][skills].
- INFERRED dimensions: merchant segment; product; data completeness (full / missing cost basis / conflicting); request type (new quote, renegotiation, competitor match); constraint (margin floor, promo).
- INFERRED: keep frozen baseline-vs-corrected cases separate from the calibration test set; version both.

## 4. Judge prompt: unsupported_pricing_justification
- Prereqs: error analysis done, ≥20 Pass and ≥20 Fail human labels, code check ruled out [skills]; red-team the failure at least once [faq].
- One failure mode per judge, never holistic [faq][skills].
- INFERRED: numeric checks (quoted rate = rate card; cited numbers appear in tool results) go to code; judge handles semantic grounding only.
- Inputs: history + tool call + tool result, as snippets [skills]; confirm via ablation [faq].
- Most capable affordable model; pin exact version [judge][skills].

Skeleton (structure [judge][skills]; wording INFERRED):
```
You are a senior merchant-pricing reviewer.
Task: judge ONE criterion: is every pricing claim in the
justification supported by the tool results or policy below?

PASS: every rate, fee, discount, margin and stated reason
traces to a tool result or policy line.
FAIL: any claim or figure that cannot be traced.
{{error-analysis category definition}}

Policy reference: {{policy_snippets}}

<examples>  <!-- train split only, 2-4: Pass, Fail, borderline -->
<example-1>
 <merchant_context>…</merchant_context>
 <tool_results>…</tool_results>
 <justification>…</justification>
 <critique>{"critique":"…","result":"Fail"}</critique>
</example-1>
</examples>

<merchant_context>{{merchant}}</merchant_context>
<tool_results>{{rate_card}} {{cost_basis}}</tool_results>
<justification>{{agent_justification}}</justification>

Write a detailed critique first, then the verdict.
```
- Output via Anthropic tool schema `{"critique": string, "result": "Pass"|"Fail"}`, critique first [skills].
- Critiques: detailed enough for a new employee; Pass critiques may name flaws but say why it passes; Fail critiques name the critical element [judge].
- Examples carry the context the expert saw and are diverse [judge]; gains plateau at 4–8 [skills].
- Severity = multiple binary judges [judge][skills].

## 5. Validation math + reporting
- Polarity CONFLICT: positive = Pass [skills]; positive = error present [faq]. INFERRED: Pass = "justification supported", fixed in schema and UI, or TPR/TNR and correction silently flip.
- TPR = (judge Pass ∧ human Pass)/human Pass; TNR = (judge Fail ∧ human Fail)/human Fail [skills]. Report separately, never accuracy or kappa [judge][skills]: always-Pass at 5% error scores 95% agreement [judge].
- Target >90% both on dev; minimum 80% [skills]; FAQ sets none [faq].
- Hand-review every disagreement before automated tuning [faq][skills]: false Pass → tighten FAIL; false Fail → clarify PASS; both low → stronger model; plateau → split criterion [skills]. Never iterate after seeing test [skills].
- Rogan-Gladen: θ = (p_obs + TNR − 1)/(TPR + TNR − 1), clip [0,1], invalid when denominator ≈ 0; TPR .92, TNR .88, p_obs .80 → .85 [skills].
- 95% CI: 2,000 bootstrap resamples of test (human, judge) pairs, recompute TPR/TNR/θ, 2.5th/97.5th percentiles [skills].
- Small samples: <60 labels → CI too wide [judge][skills]; raising TPR narrows CI more than TNR [skills]. INFERRED: on 30–50-case frozen sets also resample the unlabelled set.
- Re-validate after prompt/model change [skills].
- INFERRED calibration page: confusion matrix with per-class n, TPR/TNR, CI; warn if a class <30 per split or total <60; human-vs-judge critique inspector; single-use test button (`test_consumed`).

## 6. Experiments, regression, release gate
- Partial progress as binary sub-checks ("4 of 5 facts") [faq].
- Pass-all rate with per-check drill-down; blocking vs tolerable checks; no weighted composite [faq].
- 100% pass means evals aren't challenging; ~70% can be healthy [faq].
- CI: small curated set, deterministic checks preferred; a saturated critical judge still runs before release [faq].
- Every fix gets an assertion or specialised judge [judge]; feed production failures into CI [faq].
- Production: async sampling + judges; investigate when the CI lower bound crosses threshold [faq].
- No LLM judge as synchronous guardrail [faq].
- INFERRED: baseline vs corrected agent on the same frozen cases, same pinned judge, paired case-by-case.
- INFERRED gate, block if any:
  - blocking deterministic check fails on the frozen set;
  - corrected pass-rate CI lower bound below threshold (never raw judge rate);
  - judge test TPR or TNR <80%, or <~60 test labels;
  - judge prompt/model hash changed since validation.

## 7. Anti-patterns
- Generic off-the-shelf metrics; ROUGE/BERTScore/cosine as primary [faq][judge][skills].
- Likert scales; too many metrics [faq][judge][skills].
- Rubric, categories or judge before reading traces; evaluators for imagined failures [faq][judge][skills].
- Holistic judge; judge where code would do [faq][skills].
- No domain expert [judge]; unpinned model alias [skills].
- Dev/test examples as few-shot; dev numbers as final; point estimates without CI [faq][skills]; uncorrected judge rates [faq].
- Terse or context-free critiques; non-diverse examples [judge].
- Error analysis as a one-time step [faq].
